# Requirements Document

## Introduction

The project's core logic has grown to a point where untested edge cases in pure functions
and domain models create risk ahead of planned refactors (e.g., model selection, cost
calculation). This feature defines a unit test strategy and implements tests for all
functions and methods in the core files that are exercisable without mocking external
services (database, LLM APIs, HTTP). Property-based tests using Hypothesis are added
wherever the function's behaviour must hold across a range of inputs.

The scope covers:
- `src/models/domain.py` — Pydantic domain models with mutation and validation logic
- `src/models/api.py` — already partially covered; gaps filled here
- `src/core/research_manager.py` — pure/near-pure methods
- `src/core/usage_tracker.py` — ContextVar-based session tracking
- `src/agents/qa_agent.py` — `is_quality_request()` string classifier
- `src/agents/brave_search_tool.py` — result formatting and response parsing
- `src/agents/verification_tools.py` — `parse_verification_result()` dispatcher
- `src/export/models.py` — title derivation, filename generation, timestamp helper

---

## Glossary

- **System**: the deep-research Python application
- **Test_Suite**: the collection of pytest test files under `tests/`
- **Pure_Function**: a function whose output depends only on its inputs and that has no
  observable side effects (no I/O, no global mutation)
- **Near_Pure_Method**: a method that reads or mutates only in-memory object state and
  makes no network or database calls
- **Property_Test**: a Hypothesis-driven test that asserts an invariant holds for all
  inputs generated by a strategy
- **Example_Test**: a pytest test that asserts a specific known input produces a specific
  known output
- **AgentUsage**: `src/models/domain.AgentUsage` — per-agent token and tool-call counters
- **SessionUsage**: `src/models/domain.SessionUsage` — aggregate usage across all agents
- **ResearchManager**: `src/core/research_manager.ResearchManager` — orchestration class
- **UsageTracker**: `src/core/usage_tracker` module — ContextVar-based session binding
- **QA_Agent_Module**: `src/agents/qa_agent` module
- **BraveSearchTool**: `src/agents/brave_search_tool` module
- **VerificationTools**: `src/agents/verification_tools` module
- **ExportModels**: `src/export/models` module

## Requirements

### Requirement 1: AgentUsage token accumulation

**User Story:** As a developer, I want `AgentUsage.add_tokens()` to correctly accumulate
input and output token counts, so that cost calculations are never silently wrong.

#### Acceptance Criteria

1. THE `AgentUsage` SHALL initialise `input_tokens` and `output_tokens` to `0`.
2. WHEN `add_tokens(input_tokens, output_tokens)` is called once, THE `AgentUsage` SHALL
   reflect the exact values passed.
3. WHEN `add_tokens` is called multiple times, THE `AgentUsage` SHALL accumulate totals
   correctly (sum invariant).
4. FOR ALL non-negative integer pairs `(a, b)` and `(c, d)`, calling `add_tokens(a, b)`
   then `add_tokens(c, d)` SHALL produce `input_tokens == a + c` and
   `output_tokens == b + d` (property test).
5. WHEN `add_tokens` is called with `0, 0`, THE `AgentUsage` totals SHALL remain
   unchanged (idempotence of zero).

---

### Requirement 2: AgentUsage tool-call counting

**User Story:** As a developer, I want `AgentUsage.add_tool_call()` to correctly count
tool invocations per tool name, so that per-tool cost attribution is accurate.

#### Acceptance Criteria

1. WHEN `add_tool_call(tool_name)` is called for a new tool, THE `AgentUsage` SHALL
   create an entry with count `1`.
2. WHEN `add_tool_call(tool_name)` is called `n` times for the same tool, THE
   `AgentUsage` SHALL record count `n` for that tool.
3. WHEN `add_tool_call(tool_name, count=k)` is called, THE `AgentUsage` SHALL add `k`
   to the existing count for that tool.
4. FOR ALL non-empty strings `t` and positive integers `n`, calling `add_tool_call(t)`
   `n` times SHALL produce `tool_calls[t] == n` (property test).
5. WHEN `add_tool_call` is called for two distinct tool names, THE `AgentUsage` SHALL
   maintain independent counts for each tool.

---

### Requirement 3: SessionUsage aggregate accumulation

**User Story:** As a developer, I want `SessionUsage.add_agent_usage()` to correctly
aggregate tokens across multiple agents, so that session-level totals are always
consistent with per-agent totals.

#### Acceptance Criteria

1. WHEN `add_agent_usage(agent_name, input_tokens, output_tokens)` is called for a new
   agent, THE `SessionUsage` SHALL create an `AgentUsage` entry for that agent.
2. WHEN `add_agent_usage` is called for an existing agent, THE `SessionUsage` SHALL
   accumulate tokens into the existing `AgentUsage` entry.
3. THE `SessionUsage` `total_input_tokens` SHALL always equal the sum of
   `input_tokens` across all agent entries (invariant).
4. THE `SessionUsage` `total_output_tokens` SHALL always equal the sum of
   `output_tokens` across all agent entries (invariant).
5. FOR ALL sequences of `(agent_name, input, output)` triples, the session totals SHALL
   equal the element-wise sums of the per-agent values (property test).

---

### Requirement 4: SessionUsage tool-call aggregation

**User Story:** As a developer, I want `SessionUsage.add_tool_call()` to correctly
aggregate tool calls at both the agent and session level.

#### Acceptance Criteria

1. WHEN `add_tool_call(agent_name, tool_name)` is called, THE `SessionUsage` SHALL
   increment the count in `total_tool_calls[tool_name]`.
2. WHEN `add_tool_call(agent_name, tool_name)` is called, THE `SessionUsage` SHALL
   also increment the count in `agents[agent_name].tool_calls[tool_name]`.
3. THE `SessionUsage` `total_tool_calls` count for a tool SHALL equal the sum of that
   tool's count across all agent entries (invariant).

### Requirement 5: ExtractedClaim field validator

**User Story:** As a developer, I want the `ExtractedClaim.validate_importance_controversy`
validator to enforce that highly controversial claims are never marked as low importance,
so that the fact-checking pipeline never under-prioritises risky claims.

#### Acceptance Criteria

1. WHEN an `ExtractedClaim` is constructed with `controversy_level="highly_controversial"`
   and `importance="low"`, THE `ExtractedClaim` SHALL coerce `importance` to `"medium"`.
2. WHEN an `ExtractedClaim` is constructed with `controversy_level="highly_controversial"`
   and `importance` set to any value other than `"low"`, THE `ExtractedClaim` SHALL
   preserve the original `importance` value.
3. WHEN an `ExtractedClaim` is constructed with any `controversy_level` other than
   `"highly_controversial"`, THE `ExtractedClaim` SHALL preserve the `importance` value
   unchanged regardless of its value.
4. FOR ALL valid combinations of `controversy_level` and `importance`, the validator
   SHALL produce a valid `ExtractedClaim` without raising a `ValidationError`
   (property test).

### Requirement 6: FinalReportData factory method

**User Story:** As a developer, I want `FinalReportData.from_writer_and_verification()`
to correctly populate all derived fields, so that report metadata is always consistent
with the underlying data.

#### Acceptance Criteria

1. WHEN `from_writer_and_verification` is called, THE `FinalReportData` SHALL copy
   `short_summary`, `markdown_report`, and `follow_up_questions` from the
   `WriterOutput` argument unchanged.
2. WHEN `from_writer_and_verification` is called, THE `FinalReportData`
   `total_claims_checked` SHALL equal the number of claims in `verified_claims`.
3. WHEN `from_writer_and_verification` is called, THE `FinalReportData`
   `dubious_claims_count` SHALL equal the number of claims whose `confidence_score`
   is strictly less than `FACT_CHECK_CONFIDENCE_THRESHOLD`.
4. WHEN `from_writer_and_verification` is called with `was_edited=False`, THE
   `FinalReportData` `was_edited` SHALL be `False`.
5. FOR ALL lists of `SingleClaimCitation` objects, `dubious_claims_count` SHALL equal
   `len([c for c in claims if c.confidence_score < FACT_CHECK_CONFIDENCE_THRESHOLD])`
   (property test).

### Requirement 7: ResearchManager._normalize_json_payload

**User Story:** As a developer, I want `_normalize_json_payload()` to safely convert any
input type to a plain dict, so that session loading never crashes on unexpected payload
shapes.

#### Acceptance Criteria

1. WHEN `_normalize_json_payload(None)` is called, THE `ResearchManager` SHALL return
   an empty dict `{}`.
2. WHEN `_normalize_json_payload(d)` is called with a `dict` argument, THE
   `ResearchManager` SHALL return that dict unchanged.
3. WHEN `_normalize_json_payload(s)` is called with a valid JSON object string, THE
   `ResearchManager` SHALL return the parsed dict.
4. WHEN `_normalize_json_payload(s)` is called with an invalid JSON string, THE
   `ResearchManager` SHALL return an empty dict `{}`.
5. WHEN `_normalize_json_payload(s)` is called with a valid JSON string that decodes to
   a non-dict value (e.g., a list or integer), THE `ResearchManager` SHALL return an
   empty dict `{}`.
6. WHEN `_normalize_json_payload(m)` is called with a `Mapping` (non-dict), THE
   `ResearchManager` SHALL return a plain `dict` equivalent.
7. FOR ALL valid JSON object strings, `_normalize_json_payload` SHALL return a dict
   equal to `json.loads(s)` (property test — round-trip).

### Requirement 8: ResearchManager._get_search_budget

**User Story:** As a developer, I want `_get_search_budget()` to return the correct
search budget for each mode, so that adaptive search phases never exceed their intended
limits.

#### Acceptance Criteria

1. WHEN `_get_search_budget("no_adaptive")` is called, THE `ResearchManager` SHALL
   return `DEFAULT_NUM_SEARCHES`.
2. WHEN `_get_search_budget("deep_dive")` is called, THE `ResearchManager` SHALL
   return `DEFAULT_NUM_SEARCHES + 3`.
3. WHEN `_get_search_budget("deep_dive_gap_fill")` is called, THE `ResearchManager`
   SHALL return `DEFAULT_NUM_SEARCHES * 2`.
4. WHEN `_get_search_budget` is called with any unrecognised mode string, THE
   `ResearchManager` SHALL return `DEFAULT_NUM_SEARCHES`.

### Requirement 9: ResearchManager._compute_brave_flags

**User Story:** As a developer, I want `_compute_brave_flags()` to correctly route
searches between Brave and OpenAI, so that cost-effective mode behaves as designed.

#### Acceptance Criteria

1. WHEN `cost_effective_search` is `False`, THE `ResearchManager` SHALL return all
   `False` flags regardless of phase or search count.
2. WHEN `cost_effective_search` is `True` and `phase` is `"initial"` and `search_mode`
   is `"no_adaptive"`, THE `ResearchManager` SHALL return all `True` flags.
3. WHEN `cost_effective_search` is `True` and `phase` is `"deep_dive"`, THE
   `ResearchManager` SHALL return `ceil(n/2)` `True` flags followed by `False` flags.
4. WHEN `cost_effective_search` is `True` and `phase` is `"gap_fill"`, THE
   `ResearchManager` SHALL return `ceil(n/2)` `True` flags followed by `False` flags.
5. WHEN `cost_effective_search` is `True` and `phase` is `"initial"` and `search_mode`
   is not `"no_adaptive"`, THE `ResearchManager` SHALL return all `True` flags.
6. THE length of the returned flags list SHALL always equal the number of searches
   passed in (invariant — property test).

### Requirement 10: ResearchManager.calculate_total_cost

**User Story:** As a developer, I want `calculate_total_cost()` to produce a correct
cost figure from in-memory usage data, so that I can trust the cost display before
refactoring the model selection logic.

#### Acceptance Criteria

1. WHEN `session_usage` contains no agents and no tool calls, THE `ResearchManager`
   SHALL return `0.0`.
2. WHEN `session_usage` contains a known agent with known token counts, THE
   `ResearchManager` SHALL return the expected cost computed from `MODEL_COSTS` rates.
3. WHEN `session_usage` contains tool calls, THE `ResearchManager` SHALL add
   `TOOL_COSTS[tool_name] * count` to the total.
4. WHEN `session_usage` contains an agent name not present in `AGENT_MODEL_MAP`, THE
   `ResearchManager` SHALL skip that agent without raising an exception.
5. FOR ALL non-negative token counts and tool-call counts, `calculate_total_cost` SHALL
   return a non-negative float (property test).

### Requirement 11: ResearchManager._format_cost_summary_from_snapshot

**User Story:** As a developer, I want `_format_cost_summary_from_snapshot()` to produce
a correctly formatted cost summary string from a snapshot dict, so that the UI always
displays accurate session cost data.

#### Acceptance Criteria

1. WHEN called with `None`, THE `ResearchManager` SHALL return a string containing
   "No cost data available".
2. WHEN called with an empty dict `{}`, THE `ResearchManager` SHALL return a string
   containing "No cost data available".
3. WHEN called with a valid snapshot dict, THE `ResearchManager` SHALL include the
   `total_input_tokens`, `total_output_tokens`, `total_tool_calls`, and `total_cost`
   values in the returned string.
4. WHEN called with a valid snapshot dict, THE `ResearchManager` SHALL format
   `total_cost` to 4 decimal places.

### Requirement 12: ResearchManager.reset_session_state

**User Story:** As a developer, I want `reset_session_state()` to fully clear all
in-memory session state, so that a new research run never inherits data from a previous
one.

#### Acceptance Criteria

1. WHEN `reset_session_state()` is called, THE `ResearchManager` SHALL set `report` to
   `None`.
2. WHEN `reset_session_state()` is called, THE `ResearchManager` SHALL set
   `search_results` to an empty list.
3. WHEN `reset_session_state()` is called, THE `ResearchManager` SHALL set `last_query`
   to `None`.
4. WHEN `reset_session_state()` is called, THE `ResearchManager` SHALL set
   `session_usage` to a fresh `SessionUsage()` instance.
5. WHEN `reset_session_state()` is called, THE `ResearchManager` SHALL set
   `current_session_id` to `None`.
6. WHEN `reset_session_state()` is called, THE `ResearchManager` SHALL set `cost` to
   `0.0` and `input_tokens` and `output_tokens` to `0`.
7. WHEN `reset_session_state()` is called, THE `ResearchManager` SHALL set `search_mode`
   to `SEARCH_MODE_DEFAULT`.

### Requirement 13: UsageTracker ContextVar round-trip

**User Story:** As a developer, I want the `UsageTracker` module's `set_session_usage`
and `get_session_usage` functions to correctly bind and retrieve a `SessionUsage`
instance within the same context, so that agent callbacks always update the right session.

#### Acceptance Criteria

1. WHEN `set_session_usage(session_usage)` is called and then `get_session_usage()` is
   called in the same context, THE `UsageTracker` SHALL return the same object.
2. WHEN `set_session_usage(None)` is called, THE `UsageTracker` `get_session_usage()`
   SHALL return `None`.
3. WHEN `record_agent_usage(agent_name, usage)` is called with a bound `SessionUsage`,
   THE `UsageTracker` SHALL delegate to `session_usage.add_agent_usage`.
4. WHEN `record_agent_usage` is called with no bound session (`None`), THE
   `UsageTracker` SHALL return without raising an exception.
5. WHEN `record_tool_call(agent_name, tool_name)` is called with a bound `SessionUsage`,
   THE `UsageTracker` SHALL delegate to `session_usage.add_tool_call`.
6. WHEN `record_tool_call` is called with no bound session, THE `UsageTracker` SHALL
   return without raising an exception.

### Requirement 14: is_quality_request classifier

**User Story:** As a developer, I want `is_quality_request()` to correctly identify
quality/bias analysis requests, so that the QA agent routes them to the right tool.

#### Acceptance Criteria

1. WHEN `is_quality_request("/quality")` is called, THE `QA_Agent_Module` SHALL return
   `True`.
2. WHEN `is_quality_request("/bias")` is called, THE `QA_Agent_Module` SHALL return
   `True`.
3. WHEN `is_quality_request` is called with a message containing a known trigger phrase
   (e.g., `"run bias analysis"`), THE `QA_Agent_Module` SHALL return `True`.
4. WHEN `is_quality_request` is called with a message that does not match any command
   or trigger phrase, THE `QA_Agent_Module` SHALL return `False`.
5. WHEN `is_quality_request` is called with a message containing leading/trailing
   whitespace around a command, THE `QA_Agent_Module` SHALL return `True`.
6. FOR ALL strings that do not contain any known command or trigger phrase,
   `is_quality_request` SHALL return `False` (property test).

### Requirement 15: BraveSearchTool result formatting

**User Story:** As a developer, I want `_format_brave_results()` and
`_process_search_response()` to correctly transform raw API data, so that search results
are always presented in a consistent format.

#### Acceptance Criteria

1. WHEN `_format_brave_results([])` is called, THE `BraveSearchTool` SHALL return
   `"No Brave results found."`.
2. WHEN `_format_brave_results(results)` is called with a non-empty list, THE
   `BraveSearchTool` SHALL include each result's title, URL, and description.
3. WHEN `_format_brave_results(results)` is called with more than `MAX_BRAVE_RESULTS`
   items, THE `BraveSearchTool` SHALL include at most `MAX_BRAVE_RESULTS` results.
4. WHEN `_format_brave_results(results)` is called with a result missing `"title"`,
   THE `BraveSearchTool` SHALL substitute `"Untitled"`.
5. WHEN `_process_search_response(payload)` is called with a valid API response dict,
   THE `BraveSearchTool` SHALL return the list at `payload["web"]["results"]`.
6. WHEN `_process_search_response(payload)` is called with a dict missing the `"web"`
   key, THE `BraveSearchTool` SHALL return an empty list.
7. WHEN `_process_search_response(payload)` is called with a non-dict value, THE
   `BraveSearchTool` SHALL return an empty list.

### Requirement 16: parse_verification_result dispatcher

**User Story:** As a developer, I want `parse_verification_result()` to correctly
dispatch between single and group verification results, so that the fact-checking
pipeline always receives the right type.

#### Acceptance Criteria

1. WHEN `parse_verification_result(result)` is called with a dict containing
   `"verified_claims"`, THE `VerificationTools` SHALL return a list of
   `SingleClaimCitation` objects.
2. WHEN `parse_verification_result(result)` is called with a dict that does not contain
   `"verified_claims"`, THE `VerificationTools` SHALL return a single
   `SingleClaimCitation` object.
3. WHEN `parse_verification_result` is called with a group result containing `n` claims,
   THE `VerificationTools` SHALL return a list of length `n`.

### Requirement 17: ExportModels pure helpers

**User Story:** As a developer, I want the pure helper methods on `MetadataHeader` and
`ExportResult` to behave correctly across all valid inputs, so that export filenames and
document titles are always well-formed.

#### Acceptance Criteria

1. WHEN `MetadataHeader.derive_title(header, initial_prompt)` is called with a non-empty
   `header`, THE `ExportModels` SHALL return `header` unchanged.
2. WHEN `MetadataHeader.derive_title(None, initial_prompt)` is called with a prompt of
   120 characters or fewer, THE `ExportModels` SHALL return `initial_prompt` unchanged.
3. WHEN `MetadataHeader.derive_title(None, initial_prompt)` is called with a prompt
   longer than 120 characters, THE `ExportModels` SHALL return the first 120 characters
   followed by `"…"`.
4. FOR ALL non-empty strings `h`, `derive_title(h, any_prompt)` SHALL return `h`
   (property test).
5. FOR ALL strings of length ≤ 120, `derive_title(None, s)` SHALL return `s`
   (property test).
6. WHEN `ExportResult.filename_for(session_id, ExportFormat.markdown)` is called, THE
   `ExportModels` SHALL return a string ending in `".md"`.
7. WHEN `ExportResult.filename_for(session_id, ExportFormat.pdf)` is called, THE
   `ExportModels` SHALL return a string ending in `".pdf"`.
8. WHEN `ExportResult.filename_for(session_id, ExportFormat.docx)` is called, THE
   `ExportModels` SHALL return a string ending in `".docx"`.
9. FOR ALL valid `ExportFormat` values, `filename_for` SHALL return a string containing
   the `session_id` (property test).
