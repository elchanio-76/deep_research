# Requirements Document

## Introduction

This feature introduces Alembic-based database migrations to the research assistant project. Currently, the database schema is managed via inline DDL statements (`CREATE TABLE IF NOT EXISTS`, `ALTER TABLE ADD COLUMN IF NOT EXISTS`) executed at application startup in `src/db/pool.py`. This approach lacks version tracking, rollback capability, and a structured migration history — all of which become critical as the schema evolves.

The goal is to refactor the existing schema management to use Alembic as the single source of truth for DDL, while preserving the existing asyncpg connection pool for all runtime queries. SQLAlchemy is introduced only as a dependency for Alembic's migration engine — the project does not adopt the SQLAlchemy ORM for application-level data access.

## Glossary

- **Alembic**: A lightweight database migration tool for use with SQLAlchemy. It manages schema changes through versioned migration scripts.
- **Migration_Script**: A Python file generated by Alembic that contains `upgrade()` and `downgrade()` functions representing a single schema change.
- **Migration_History**: The ordered sequence of applied Migration_Scripts tracked by Alembic in the `alembic_version` table.
- **Pool_Module**: The `src/db/pool.py` module that manages the asyncpg connection pool lifecycle.
- **Init_DB**: The `init_db()` function in Pool_Module that currently creates the connection pool and executes inline DDL.
- **Alembic_Env**: The `env.py` file inside the Alembic migrations directory that configures how Alembic connects to the database and runs migrations.
- **DATABASE_URL**: The environment variable holding the PostgreSQL connection string used by both the application and Alembic.
- **Inline_DDL**: The `CREATE TABLE IF NOT EXISTS`, `ALTER TABLE ADD COLUMN IF NOT EXISTS`, and `CREATE INDEX IF NOT EXISTS` statements currently embedded in Init_DB.
- **Initial_Migration**: The first Migration_Script that captures the full current schema (sessions table, messages table, and all indexes).
- **Downgrade**: The process of reverting a Migration_Script by executing its `downgrade()` function, undoing the schema change.
- **Schema_Drift_Check**: Sanity checks performed by Init_DB after pool creation to verify that expected tables and the Alembic migration version exist before the application fully initializes.
- **Test_Database**: A temporary PostgreSQL database created for integration tests, derived from the main database name with a `_test` suffix, and dropped after the test run completes.

## Requirements

### Requirement 1: Alembic Project Initialization

**User Story:** As a developer, I want Alembic configured in the project with a standard directory layout, so that I have a consistent framework for creating and running migrations.

#### Acceptance Criteria

1. THE Alembic_Env SHALL be configured inside an `alembic/` directory at the project root containing `env.py`, `script.py.mako`, and a `versions/` subdirectory.
2. THE project root SHALL contain an `alembic.ini` file that references the `alembic/` directory as the script location.
3. WHEN Alembic reads its configuration, THE Alembic_Env SHALL resolve the database connection string from the DATABASE_URL environment variable.
4. THE `alembic.ini` file SHALL NOT contain any hardcoded database credentials or connection strings.
5. THE `requirements.txt` file SHALL include `alembic` and `sqlalchemy` as project dependencies with pinned versions.

### Requirement 2: Initial Migration Capturing Current Schema

**User Story:** As a developer, I want the existing database schema captured in a versioned migration script, so that the current state is tracked and reproducible from a clean database.

#### Acceptance Criteria

1. THE Initial_Migration SHALL contain an `upgrade()` function that creates the `sessions` table with all columns and defaults matching the current Inline_DDL.
2. THE Initial_Migration SHALL contain an `upgrade()` function that creates the `messages` table with all columns, the foreign key constraint on `session_id`, and the `ON DELETE CASCADE` behavior matching the current Inline_DDL.
3. THE Initial_Migration SHALL create the `idx_sessions_last_activity` index on `sessions(last_activity_at DESC)`.
4. THE Initial_Migration SHALL create the `idx_messages_session_id` index on `messages(session_id)`.
5. THE Initial_Migration SHALL contain a `downgrade()` function that drops the `messages` table before the `sessions` table, respecting the foreign key dependency order.
6. WHEN the Initial_Migration `upgrade()` is run against an empty database, THE database SHALL contain the `sessions` table, the `messages` table, and both indexes with schemas identical to those produced by the current Inline_DDL.

### Requirement 3: Removal of Inline DDL from Application Startup

**User Story:** As a developer, I want schema management handled exclusively by Alembic, so that there is a single source of truth for the database schema and no conflicting DDL paths.

#### Acceptance Criteria

1. THE Init_DB function SHALL NOT execute any `CREATE TABLE`, `ALTER TABLE`, or `CREATE INDEX` statements.
2. THE Init_DB function SHALL continue to create and return the asyncpg connection pool.
3. THE Pool_Module SHALL preserve the `get_pool()`, `init_db()`, and `close_pool()` public interface without signature changes.
4. WHEN the FastAPI application starts, THE lifespan handler SHALL continue to call Init_DB to obtain the connection pool.
5. THE `src/db/sessions.py` and `src/db/messages.py` query modules SHALL remain unchanged, continuing to use the asyncpg pool for all runtime queries.

### Requirement 4: Rollback Capability

**User Story:** As a developer, I want the ability to roll back any migration, so that I can revert schema changes that cause problems in development or staging.

#### Acceptance Criteria

1. THE Initial_Migration SHALL include a `downgrade()` function that fully reverses the `upgrade()` by dropping all created tables and indexes.
2. WHEN `alembic downgrade -1` is executed after the Initial_Migration has been applied, THE database SHALL no longer contain the `sessions` table, the `messages` table, or their indexes.
3. WHEN `alembic downgrade -1` is executed and then `alembic upgrade head` is executed, THE database schema SHALL be identical to the schema produced by running `upgrade` alone.

### Requirement 5: Migration Execution via Alembic CLI

**User Story:** As a developer, I want to manage migrations using standard Alembic CLI commands, so that the workflow is familiar and well-documented.

#### Acceptance Criteria

1. WHEN `alembic upgrade head` is executed, THE Alembic_Env SHALL apply all pending Migration_Scripts in order up to the latest revision.
2. WHEN `alembic downgrade -1` is executed, THE Alembic_Env SHALL revert the most recently applied Migration_Script by calling its `downgrade()` function.
3. WHEN `alembic current` is executed, THE Alembic_Env SHALL display the currently applied migration revision.
4. WHEN `alembic history` is executed, THE Alembic_Env SHALL display the full Migration_History with revision identifiers and descriptions.
5. WHEN `alembic revision -m "<description>"` is executed, THE Alembic_Env SHALL generate a new Migration_Script in the `versions/` directory with empty `upgrade()` and `downgrade()` functions.

### Requirement 6: Schema Drift Detection at Startup

**User Story:** As a developer, I want the application to detect missing migrations at startup, so that I get a clear error message instead of cryptic PostgreSQL failures when I forget to run `alembic upgrade head`.

#### Acceptance Criteria

1. WHEN `init_db()` creates the connection pool, THE function SHALL verify that the `sessions` table exists in the database.
2. WHEN `init_db()` creates the connection pool, THE function SHALL verify that the `messages` table exists in the database.
3. WHEN `init_db()` creates the connection pool, THE function SHALL verify that the `alembic_version` table exists and contains at least one revision row.
4. IF any of the expected tables (`sessions`, `messages`) do not exist, THEN `init_db()` SHALL raise a `RuntimeError` with a message instructing the developer to run `alembic upgrade head`.
5. IF the `alembic_version` table does not exist or contains no rows, THEN `init_db()` SHALL raise a `RuntimeError` with a message instructing the developer to run `alembic upgrade head`.
6. THE schema drift checks SHALL execute after the connection pool is created but before the pool is returned to the caller.

### Requirement 7: Dedicated Test Database for Integration Tests

**User Story:** As a developer, I want integration tests to run against an isolated temporary database, so that tests do not read or modify real application data.

#### Acceptance Criteria

1. WHEN the integration test suite starts, THE test infrastructure SHALL create a temporary PostgreSQL database whose name is derived from the main database name with a `_test` suffix.
2. WHEN the temporary test database is created, THE test infrastructure SHALL run `alembic upgrade head` against it to apply all migrations.
3. WHEN the integration test suite completes (whether tests pass or fail), THE test infrastructure SHALL drop the temporary test database.
4. THE integration tests SHALL use a pytest fixture (session-scoped) that manages the test database lifecycle: create, migrate, provide connection, and drop.
5. THE integration tests SHALL NOT read from or write to the main application database.

### Requirement 8: Alembic Environment Configuration

**User Story:** As a developer, I want the Alembic environment to integrate cleanly with the project's existing configuration, so that I do not need to maintain separate database connection settings.

#### Acceptance Criteria

1. THE Alembic_Env SHALL load environment variables from the `.env` file using `python-dotenv` before resolving DATABASE_URL.
2. IF the DATABASE_URL environment variable is not set, THEN THE Alembic_Env SHALL raise a clear error message indicating the missing variable.
3. THE Alembic_Env SHALL run migrations synchronously using a standard SQLAlchemy engine (Alembic's default mode), independent of the application's async runtime.
4. THE Alembic_Env SHALL support both `--sql` (offline) and online migration modes as provided by Alembic's default `env.py` patterns.
5. THE Alembic_Env SHALL accept an optional database URL override (e.g., via `x_argument`) to support running migrations against a test database.
